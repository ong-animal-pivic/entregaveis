Teste unitário, teste de integração e teste de API

Três camadas diferentes de "robôs" que conferem sozinhos se o sistema continua funcionando corretamente — o que cada uma testa, por que existem as três, e quando cada uma é usada.

Este material foi estudado a partir da etapa de testes automatizados da API de adotantes — ver relatório be-testes-integracao-api-2026-09-05.

1. O que é

Um teste automatizado é um "robô" que simula uma ação de uso do sistema e confere sozinho se o resultado é o esperado — sem precisar de uma pessoa clicando manualmente em cada tela para verificar se tudo continua funcionando. Existem diferentes "níveis" de teste automatizado, que diferem no tamanho do pedaço do sistema que cada um verifica de cada vez.

Uma analogia

Pense na fabricação de um carro. Primeiro, cada peça é testada isolada na bancada (o motor sozinho, o freio sozinho) — isso é o teste unitário. Depois, testa-se se as peças se encaixam e funcionam bem juntas, ainda dentro da fábrica (o motor ligado ao câmbio) — isso é o teste de integração. Por fim, testa-se o carro inteiro rodando na pista, usando o volante e os pedais exatamente como um motorista usaria — isso é o teste de API (ou teste "de ponta a ponta").

Teste unitário

Uma peça isolada

Confere uma única regra ou cálculo, isolado do resto do sistema (sem banco de dados, sem outras partes envolvidas).

Teste de integração

Peças conectadas

Confere se duas ou mais partes do sistema funcionam corretamente quando conectadas entre si (ex: a lógica de negócio conversando de verdade com o banco de dados).

Teste de API

O sistema inteiro, de fora

Confere o sistema como um todo, entrando exatamente pela mesma "porta de entrada" que a tela usaria — sem conhecer nem se importar com o que existe por dentro.

2. Que problema cada um resolve

Sem cada uma dessas camadas, um tipo diferente de problema passaria despercebido até tarde demais:

  • Sem teste unitário: um erro numa regra isolada (ex: um cálculo com a conta errada) só seria percebido depois, quando já estivesse misturado com o resto do sistema — mais difícil e demorado de localizar exatamente onde o erro está.
  • Sem teste de integração: cada peça isolada poderia estar "correta" na bancada, mas ainda assim não se encaixar direito com as outras (ex: a lógica de negócio manda salvar algo do jeito errado para o banco de dados) — um problema que só aparece quando as partes se conectam de verdade.
  • Sem teste de API: mesmo com as peças testadas e encaixadas, a "porta de entrada" do sistema (o jeito que a tela efetivamente conversa com ele) poderia ter um problema que só apareceria quando alguém realmente tentasse usar o sistema — ou seja, só seria descoberto em produção, com o sistema já em uso real.

3. Como funciona

As três camadas formam o que costuma ser chamado de pirâmide de testes: muitos testes unitários (rápidos e baratos de rodar), uma quantidade média de testes de integração, e poucos testes de API (mais lentos, pois precisam ligar o sistema quase inteiro para rodar).

Teste unitário — exemplo genérico

Pseudo-código ilustrativo — não representa código real do projeto

teste "calcula desconto de 10% corretamente":
    resultado = ServicoDeDesconto.calcular(precoBase: 100)
    esperar(resultado) igual a 90

Chama diretamente uma única peça de lógica (ServicoDeDesconto), sem banco de dados nem rede envolvidos — só a conta em si.

Teste de integração — exemplo genérico

Pseudo-código ilustrativo — não representa código real do projeto

teste "salva um pedido de verdade no banco":
    ServicoDePedido.criar(pedido: novoPedido)
    resultado = BancoDeDados.buscar(novoPedido.id)
    esperar(resultado) não seja vazio

Chama a lógica de negócio (ServicoDePedido) conectada a um banco de dados real de teste, confirmando que as duas partes conversam corretamente entre si.

Teste de API — exemplo genérico

Pseudo-código ilustrativo — não representa código real do projeto

teste "cria um pedido através da API":
    resposta = HTTP.post("/pedidos", dados: novoPedido)
    esperar(resposta.status) igual a 201
    esperar(resposta.corpo.id) não seja vazio

Não chama nenhuma classe do sistema diretamente — faz uma chamada HTTP real, como a própria tela faria, e confere só a resposta que chega "de fora".

Relação com a arquitetura em camadas

Num sistema organizado em camadas — Controller (porta de entrada), Service (regras de negócio) e Repository (acesso ao banco de dados) — cada tipo de teste "abraça" uma fatia diferente dessas camadas: o teste unitário mira uma camada isolada (tipicamente o Service sozinho, sem tocar no Repository de verdade); o teste de integração mira duas ou mais camadas conectadas entre si (ex: Service + Repository + banco de dados real de teste); e o teste de API entra pela camada mais externa (Controller) e atravessa todas as camadas de uma vez, de ponta a ponta.

Padrões de nomenclatura

É comum, em projetos Java como este, usar o nome do arquivo de teste para já indicar de que tipo ele é, sem precisar abrir o conteúdo: um sufixo como Test costuma indicar teste unitário (rodado nas verificações rápidas do dia a dia), enquanto um sufixo como IT (de Integration Test) indica um teste de integração ou de API, rodado numa etapa separada e mais demorada do processo de build. Essa convenção também orienta as próprias ferramentas de build: elas podem ser configuradas para rodar automaticamente só os arquivos terminados em Test numa etapa, e só os terminados em IT em outra — foi exatamente esse tipo de configuração que precisou ser ajustada no projeto para que o novo teste de API passasse a rodar automaticamente (ver relatório be-testes-integracao-api-2026-09-05).

4. Onde isso apareceu no projeto

O backend do sistema já contava, antes de 05/09, com testes de integração no nível da lógica de negócio: eles chamam diretamente a parte responsável pelas regras de cada cadastro, mas já conectada a um banco de dados real de teste — cobrindo a camada do meio da pirâmide. Na etapa de 05/09, foi adicionado o primeiro teste de API do projeto: um teste que faz chamadas HTTP reais contra o cadastro de adotantes, cobrindo o caminho completo (criar, consultar, editar, excluir) e alguns casos de erro esperados, exatamente como a tela faria ao usar o sistema. Veja o relatório be-testes-integracao-api-2026-09-05 para os detalhes dessa etapa.

5. Armadilhas comuns e boas práticas

Armadilhas comuns

Teste unitário

Não deve depender de banco de dados, rede ou qualquer coisa "de fora" — se depender, deixa de ser rápido e passa a ser, na prática, um teste de integração disfarçado.

Teste de integração

Um teste pode deixar dados "sujos" no banco depois de rodar, atrapalhando o próximo teste que rodar em seguida — é preciso sempre limpar o que foi criado ao final de cada teste.

Teste de API

Como é mais lento e mais caro de rodar, não faz sentido repetir nele todas as combinações de erro já cobertas nos testes de camadas mais baixas — reservar para os caminhos mais importantes do ponto de vista de quem usa o sistema.

Boas práticas

Teste unitário

Nomear o teste descrevendo o comportamento esperado (ex: "calcula desconto de 10% corretamente"), não só o nome técnico do método testado — assim o próprio nome do teste já explica o que quebrou quando ele falha.

Teste de integração

Rodar sempre contra um ambiente de teste isolado (nunca contra o banco de dados real usado pelo sistema em produção), para que uma falha no teste jamais afete dados reais.

Teste de API

Conferir não só se a resposta veio com o status esperado, mas também se o formato/conteúdo da resposta é o combinado (o chamado "contrato" da API) — um status certo com dados errados também é uma falha.

6. Termos relacionados

Pirâmide de testes
Representação visual da proporção ideal entre os tipos de teste: muitos unitários, menos de integração, poucos de API.
Mock
Uma "peça falsa" usada num teste unitário para simular uma dependência (ex: um banco de dados de mentira), evitando depender de algo real.
Ambiente de teste
Uma cópia isolada do sistema (e, geralmente, do banco de dados) usada só para rodar testes, sem afetar dados reais.
CRUD
Sigla para as quatro operações básicas de um cadastro: Criar, Consultar (Read), Atualizar (Update) e Excluir (Delete).
Teste de ponta a ponta
Outro nome comum para o teste de API: testa o sistema do início ao fim, como o usuário final o utilizaria.
Convenção de nomenclatura de testes
Padrão de sufixo no nome do arquivo (ex: Test, IT) usado para indicar o tipo de teste e permitir que ferramentas de build o executem na etapa correta automaticamente.
Contrato de uma API
O formato combinado de resposta que a API promete devolver (quais campos, em que tipo) — um teste de API deve conferir se esse combinado está sendo cumprido.

Em resumo: as três camadas de teste não competem entre si — se complementam. Testes unitários dão confiança rápida sobre pedaços isolados de lógica; testes de integração confirmam que as peças se encaixam de verdade; testes de API confirmam que o sistema, usado do jeito que ele realmente é usado, funciona de ponta a ponta.
