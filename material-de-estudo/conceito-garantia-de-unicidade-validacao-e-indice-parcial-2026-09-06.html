Garantia de unicidade de dados: validação na aplicação + índice único no banco

Como o sistema garante que não existam duas raças com o mesmo nome para a mesma espécie — usando duas camadas de proteção diferentes, e por que uma sozinha não seria suficiente.

Este conceito foi estudado a partir da implementação que impede o cadastro de raças duplicadas por espécie (código do dia 06/09/2026). A coluna ativo, usada na condição do índice do banco explicado abaixo, foi introduzida anteriormente pela exclusão lógica — ver relatório be-exclusao-logica-2026-08-23.

1. O que é

Uma analogia

Imagine uma recepção de clube que não deixa cadastrar dois sócios com o mesmo apelido: o recepcionista confere na lista antes de anotar um nome novo. Mas e se dois recepcionistas, em guichês diferentes, cadastrarem dois sócios com o mesmo apelido ao mesmo tempo, cada um sem saber do outro? Para isso não acontecer de jeito nenhum, o clube também mantém um arquivo físico que fisicamente não aceita duas fichas com o mesmo apelido dentro dele — não importa quantos recepcionistas estejam trabalhando ao mesmo tempo.

Essa é a ideia por trás da garantia de unicidade de dados: impedir que duas informações "iguais" (segundo alguma regra) coexistam no sistema. Aqui ela é feita em duas camadas — uma checagem no código da aplicação (o recepcionista, rápido e com mensagem amigável) e uma constraint direto no banco de dados (o arquivo físico, mais lento de consultar, mas a prova de falhas). Quando essa segunda camada só se aplica a uma parte dos registros (por exemplo, ignorando os que foram excluídos), ela é chamada de índice único condicional ou parcial.

2. Que problema resolve

Cada uma das duas camadas, sozinha, deixa uma brecha diferente:

Só checagem na aplicação

Duas requisições de cadastro quase simultâneas podem, cada uma, checar o banco e não encontrar nada (porque a outra ainda não terminou de gravar) — e as duas seguem em frente achando que o nome está livre. Resultado: duas raças duplicadas salvas. Esse tipo de falha é chamado de condição de corrida (race condition).

Só constraint no banco

O banco impediria a duplicidade, mas a mensagem de erro seria crua e técnica (algo como "violação de índice único"), sem explicar ao usuário, em português, que já existe uma raça com aquele nome para aquela espécie.

Por isso as duas camadas coexistem: a checagem na aplicação cobre o caso comum com uma mensagem clara; a constraint no banco é a defesa final, que não depende de nenhum código da aplicação ter rodado corretamente — ela vale mesmo sob concorrência.

3. Como funciona

O trecho abaixo é real, do backend do Sistema ONG Animal (Spring Boot). Primeiro o service decide qual verificação de duplicidade rodar:

public Raca salvar(Raca raca) {

    Long especieId = raca.getEspecie().getId();
    Especie especie = especieService.buscarPorId(especieId);

    raca.setEspecie(especie);

    boolean nomeDuplicado = raca.getId() == null
            ? racaRepository.existsByNomeIgnoreCaseAndEspecieId(raca.getNome(), especieId)
            : racaRepository.existsByNomeIgnoreCaseAndEspecieIdAndIdNot(raca.getNome(), especieId, raca.getId());

    if (nomeDuplicado) {
        throw new RacaExistenteException(raca.getNome(), especie.getNome().name());
    }

    return racaRepository.save(raca);
}

RacaService.salvar() — o mesmo método atende tanto o cadastro (POST) quanto a edição (PUT) de uma raça, sem métodos separados para cada caso.

Linha a linha: raca.getId() == null é a condição que diferencia os dois cenários — se ainda não existe um identificador, é um cadastro novo; se já existe, é uma edição. No cadastro, a checagem (existsByNomeIgnoreCaseAndEspecieId) só precisa confirmar que nenhuma raça daquela espécie já usa aquele nome. Na edição, isso não seria suficiente: a própria raça sendo editada já existe no banco com aquele nome, então a variante ...AndIdNot exclui o próprio registro da comparação — senão toda edição sem troca de nome seria barrada como "duplicada de si mesma". Se a checagem der positivo, o método lança RacaExistenteException antes de chegar perto do save.

Essas duas checagens não têm corpo escrito à mão — são query methods do Spring Data JPA, que gera a consulta SQL sozinho a partir do nome do método:

public interface RacaRepository extends JpaRepository<Raca, Long> {

    boolean existsByNomeIgnoreCaseAndEspecieId(String nome, Long especieId);

    boolean existsByNomeIgnoreCaseAndEspecieIdAndIdNot(String nome, Long especieId, Long id);
}

RacaRepository — a parte IgnoreCase do nome do método já instrui o Spring a comparar sem diferenciar maiúsculas/minúsculas (equivalente a comparar as duas strings em caixa baixa).

Se a raça for realmente duplicada, o sistema lança uma exceção específica, e não um erro genérico:

public class RacaExistenteException extends EntityExistsException {
    public RacaExistenteException(String nome, String especieNome) {
        this(String.format(
            "Já existe uma raça chamada '%s' cadastrada para a espécie '%s'",
            nome, especieNome));
    }
}

RacaExistenteException — a mensagem já nasce pronta para ser lida por uma pessoa, citando o nome e a espécie em conflito.

Essa exceção é capturada por um tratador central único, que existe para todo o sistema (não só para raça), e vira uma resposta HTTP padronizada:

@ExceptionHandler(EntityExistsException.class)
public ProblemDetail handleEntityExistsException(EntityExistsException ex) {
    return createProblemDetail(HttpStatus.CONFLICT, ex.getMessage(),
            "Entidade já existente", "https://pivic-ong/entidade-existente");
}

ApiExceptionHandler — qualquer exceção do tipo EntityExistsException (família à qual RacaExistenteException pertence) vira automaticamente uma resposta HTTP 409 Conflict, no formato padronizado ProblemDetail (RFC 7807).

Por fim, a defesa que não depende de nenhum código Java ter rodado: um índice único parcial, criado direto no banco por uma migração Flyway:

CREATE UNIQUE INDEX uq_raca_nome_especie
ON raca (LOWER(nome), especie_id)
WHERE ativo = true;

V011__adiciona_constraint_unica_raca_nome_especie.sql — o banco recusa fisicamente gravar uma segunda linha com o mesmo LOWER(nome) e especie_id de uma linha já existente com ativo = true, não importa quantas requisições cheguem ao mesmo tempo.

O WHERE ativo = true existe porque a tabela raca usa exclusão lógica (soft delete): excluir uma raça só marca ativo = false, sem apagar a linha. Sem essa condição, o índice consideraria também as raças "excluídas" na comparação, e nunca mais seria possível cadastrar uma nova raça reaproveitando um nome que já foi usado por outra excluída — mesmo que ela não apareça mais para ninguém no sistema.

Arquitetura de software

A validação de duplicidade fica na camada de Service, onde vivem as regras de negócio do domínio (não no Controller, que só recebe e devolve requisições, nem no Repository, que só sabe conversar com o banco). O tratamento de erro é centralizado num único ponto (ApiExceptionHandler) para todo o sistema, em vez de cada Controller tratar sua própria exceção. Já a constraint no banco é a última linha de defesa da camada de persistência — ela não sabe nada sobre regras de negócio ou mensagens amigáveis, só garante a integridade dos dados fisicamente armazenados, mesmo que alguém escreva direto no banco por fora da aplicação.

Padrões de nomenclatura

Algumas convenções usadas aqui aparecem com frequência em projetos Spring/JPA: classes de regra de negócio terminam em *Service; interfaces de acesso a dados terminam em *Repository; exceções de domínio recebem o sufixo do problema que representam, como *ExistenteException (ou, em inglês, *ExistsException); migrações Flyway seguem o padrão V<número sequencial>__descrição_em_snake_case.sql; e índices/constraints únicas no banco costumam usar o prefixo uq_<tabela>_<colunas>, deixando claro, só pelo nome, o que ele protege.

4. Onde isso apareceu no projeto

Esse mecanismo foi implementado no backend, na funcionalidade que impede o cadastro de raças duplicadas por espécie, tocando estes arquivos:

  • RacaService (camada de serviço) — método salvar(), com a checagem de duplicidade explicada acima.
  • RacaRepository (camada de acesso a dados) — os dois query methods usados pela checagem.
  • RacaExistenteException e EntityExistsException (camada de domínio/exceções) — a exceção específica de raça e sua superclasse compartilhada.
  • ApiExceptionHandler (camada de API) — tratador central que converte a exceção em HTTP 409.
  • A migração Flyway V011, que cria o índice único parcial no banco.

A cobertura de testes de integração (RacaServiceIT) inclui os dois cenários: tentar cadastrar uma raça com nome já usado na mesma espécie, e tentar atualizar uma raça para um nome já usado por outra raça da mesma espécie — os dois devem lançar RacaExistenteException.

O mesmo padrão (checagem no Service + índice único parcial condicionado a ativo = true) ainda não foi aplicado a outros cadastros do sistema, mas seria diretamente reaproveitável: por exemplo, se um dia for necessário impedir duas espécies com o mesmo nome, a receita seria a mesma — um existsByNomeIgnoreCase no EspecieRepository, mais um índice uq_especie_nome parcial no banco.

5. Armadilhas comuns / boas práticas

  • Confiar só na checagem da aplicação: sob concorrência (duas requisições quase ao mesmo tempo), a checagem sozinha não impede duplicidade — é exatamente o problema que o índice único no banco resolve.
  • Esquecer o ...AndIdNot na atualização: usar a mesma checagem do cadastro também na edição faria toda edição de uma raça (sem trocar o nome) ser barrada como "duplicada" — duplicada dela mesma.
  • Índice sem considerar o soft delete: um índice único sem o WHERE ativo = true impediria reaproveitar um nome depois que a raça original foi excluída (logicamente), mesmo ela não aparecendo mais para ninguém.
  • Descompasso entre a comparação da aplicação e a do banco: o IgnoreCase do método do repository e o LOWER(nome) do índice precisam representar a mesma regra de comparação — senão um dos dois lados pode aceitar algo que o outro rejeitaria.

Boas práticas

Sempre que uma tabela tiver exclusão lógica, qualquer constraint de unicidade sobre ela deveria ser parcial/condicionada ao campo de "ativo" — senão registros excluídos continuam "reservando" valores para sempre. E, de forma mais geral: validar na aplicação para dar uma mensagem clara a quem usa o sistema é importante, mas nunca deveria ser a única garantia quando existe risco real de concorrência — a constraint no banco é o que efetivamente impede o dado inconsistente de existir.

6. Termos relacionados

Índice único parcial/condicional
Uma regra de unicidade no banco que só vale para os registros que satisfazem uma condição (aqui, ativo = true), em vez de valer para a tabela inteira.
Condição de corrida (race condition)
Falha que ocorre quando duas ações acontecem quase ao mesmo tempo e cada uma assume um estado do sistema que a outra ainda vai mudar.
Exclusão lógica (soft delete)
Marcar um registro como inativo (ativo = false) em vez de apagá-lo de fato do banco.
Query method
Método de uma interface de repositório (Spring Data JPA) cujo nome já descreve a consulta SQL que deve ser gerada, sem precisar escrever a query manualmente.
ProblemDetail / RFC 7807
Formato padronizado de resposta de erro em APIs REST, com campos como status, título e mensagem, em vez de cada erro ter um formato diferente.

Em resumo: garantir que um dado seja único costuma exigir duas camadas complementares — uma checagem no código da aplicação, para dar uma mensagem clara e rápida na maioria dos casos, e uma constraint no próprio banco de dados, que é a única garantia que resiste mesmo quando duas operações acontecem ao mesmo tempo. Quando a tabela usa exclusão lógica, essa constraint precisa ser parcial, considerando apenas os registros ainda ativos.
