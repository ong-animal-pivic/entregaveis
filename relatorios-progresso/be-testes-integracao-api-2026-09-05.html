Testes automatizados que simulam o uso real da API

O que foi feito para garantir, de forma automática, que o cadastro de adotantes continua funcionando corretamente do jeito que quem usa o sistema realmente o utiliza — explicado com analogias, sem entrar no código em si.

1. O que foi feito

O sistema já contava com testes automatizados que conferiam as regras de negócio "por dentro" — chamando diretamente a parte do sistema responsável pela lógica de cada cadastro, sem passar pela porta de entrada real que a tela usa. Essa etapa criou o primeiro conjunto de testes que passa exatamente pelo mesmo caminho que a tela percorre: uma chamada real à API, como se fosse a própria aplicação pedindo para cadastrar, consultar, editar ou excluir um adotante.

Uma analogia

É a diferença entre testar o motor de um carro isolado na bancada e testar o carro inteiro rodando na pista, com o motorista girando a chave, pisando no acelerador e usando o painel normalmente. Os testes que já existiam conferiam "o motor" (a lógica interna); os novos testes conferem "o carro andando" (a API sendo usada de ponta a ponta, do jeito que ela realmente é usada).

API
"Porta de entrada" do sistema, que recebe pedidos da tela e devolve respostas.
Teste automatizado
Um "robô" que simula ações de uso do sistema e confere sozinho se o resultado é o esperado, sem precisar de alguém testando manualmente.
Cenário de teste
Uma situação específica simulada pelo teste (ex: cadastrar com sucesso, ou tentar cadastrar com um dado inválido).

2. Cenários cobertos pelo novo teste

O novo conjunto de testes simula, para o cadastro de adotantes, tanto o uso correto do sistema (chamado de "caminho feliz") quanto situações em que algo dá errado de propósito, para confirmar que o sistema reage da forma esperada nesses casos também.

Caminho feliz

Cadastrar um novo adotante, depois buscá-lo pelo identificador, listar todos os adotantes, editar seus dados e, por fim, excluí-lo — confirmando que ele deixa de aparecer nas consultas seguintes.

Erro esperado

Buscar um adotante com um identificador que não existe — o sistema deve responder de forma clara que não encontrou o registro, em vez de travar ou dar um erro confuso.

Erro esperado

Tentar cadastrar um adotante usando o mesmo número de telefone tanto como principal quanto como secundário — o sistema deve recusar, respeitando a regra de que os dois telefones precisam ser diferentes.

Erro esperado

Tentar cadastrar um adotante sem preencher um campo obrigatório (o nome) — o sistema deve recusar e indicar exatamente qual campo está faltando.

3. Por que era necessário ajustar o processo de build

Junto com o novo teste, foi feito um ajuste na configuração do projeto para que esse tipo de teste passasse a ser executado automaticamente.

Uma analogia

É como uma linha de montagem que já tinha uma etapa de "inspeção rápida" (os testes mais simples e rápidos, que rodavam a cada verificação do projeto), mas não tinha uma etapa de "teste de pista" — mais demorada, pois liga o sistema inteiro para testá-lo de verdade. O ajuste feito adiciona essa segunda etapa ao processo, garantindo que, quando o projeto é validado, os testes que simulam o uso real da API também rodem, e não fiquem esquecidos ou dependendo de alguém lembrar de rodá-los manualmente.

4. Um desafio técnico resolvido: registros "excluídos" continuam existindo

O sistema já usa, desde uma etapa anterior do projeto (ver relatório be-exclusao-logica-2026-08-23), o conceito de exclusão lógica: quando um cadastro é "excluído", ele não é apagado de verdade do banco de dados — ele apenas é marcado como inativo, e passa a ser ignorado nas listagens e buscas normais.

Problema

Como o teste cadastra e "exclui" adotantes repetidamente para simular o uso real, esses registros continuavam fisicamente guardados no banco (só marcados como inativos). Isso travaria execuções futuras do teste, já que documentos como CPF e e-mail precisam ser únicos no sistema — mesmo entre registros inativos.

Solução

Ao final de cada teste, o próprio teste apaga de verdade, diretamente no banco de dados, os registros que ele mesmo criou durante a simulação — sem depender do mecanismo normal de exclusão, que apenas inativaria de novo um registro já inativo.

Em resumo: essa etapa não altera nenhuma regra de negócio nem adiciona uma tela ou funcionalidade nova — ela cria uma rede de segurança automatizada que confirma, a cada verificação futura do sistema, que o cadastro de adotantes continua funcionando corretamente do início ao fim, exatamente como quem usa o sistema o utilizaria.
