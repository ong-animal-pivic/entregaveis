PIVIC · Sistema ONG Animal · Relatório de progresso · 16/08/2026

Melhoria na forma como o sistema troca informações

O que foi alterado no sistema, por que essa mudança era importante e o que ela traz de benefício para o restante do projeto — explicado com analogias e diagramas, sem entrar no código em si.

1. O que foi feito

O sistema é dividido em três camadas que conversam entre si: a tela que o usuário usa (cadastro de animais, adotantes, etc.), a API — a "porta de entrada" do sistema que recebe os pedidos da tela — e o banco de dados, onde as informações ficam guardadas de forma permanente. Até esta mudança, a API repassava direto para a tela a mesma estrutura de dados usada para gravar no banco (chamada de entidade). Ou seja, não havia diferença entre "como o dado é guardado" e "como o dado é exposto para fora do sistema".

Uma analogia

Foi criado uma classe intermediária para cada tipo de cadastro do sistema (adotante, animal, raça e espécie). Na programação, esse padrão tem nome: DTO (Data Transfer Object, "objeto de transferência de dados"). Existe um DTO de entrada (o formulário — o que a tela envia) e um DTO de saída (o comprovante — o que a tela recebe de volta), separados da entidade que representa o dado dentro do banco.

Entidade
Estrutura de dados que representa uma tabela do banco de dados.
DTO
Estrutura de dados usada só para troca de informação entre a tela e a API.
API
"Porta de entrada" do sistema, que recebe pedidos da tela e devolve respostas.
Controller
Parte da API responsável por atender cada tipo de pedido (cadastrar, editar, consultar).

Essa mudança foi feita aos poucos, um tipo de cadastro por vez, para que cada etapa pudesse ser conferida com calma antes de seguir para a próxima.

2. Etapas realizadas

A migração para o padrão DTO foi aplicada camada por camada, sempre nesta ordem para cada cadastro: criar os DTOs de entrada e saída → ajustar o Controller para usá-los → conferir que nada quebrou.

  1. Cadastro de Adotante
    Primeiro cadastro a receber o novo formulário/comprovante — o mais completo, pois envolve dados pessoais, documento, contato e endereço.
  2. Cadastro de Espécie
    Cadastro mais simples do sistema (só é possível consultar, não cadastrar/editar por essa tela) — recebeu apenas o "comprovante" de consulta.
  3. Cadastro de Raça
    Cada raça pertence a uma espécie — essa etapa ajustou como essa ligação entre os dois cadastros é comunicada.
  4. Cadastro de Animal
    O cadastro mais completo: cada animal está ligado a uma raça e, quando adotado, a um adotante. Foi a etapa mais delicada por reunir mais informações conectadas entre si.
  5. Organização final
    Depois que todos os cadastros passaram a usar o novo formulário/comprovante, foram removidas regras de conferência de dados que ficavam "espalhadas" em dois lugares diferentes do sistema, deixando apenas um único lugar responsável por checar se as informações enviadas estão corretas.

4. Por que essa mudança era necessária

Sem esse "formulário/comprovante" intermediário, a tela do sistema tinha acesso direto à estrutura interna do banco de dados. Isso trazia alguns riscos práticos:

  • Falta de controle sobre o que é mostrado: qualquer ajuste feito no arquivo interno do banco de dados podia, sem querer, aparecer na tela do usuário ou em outros sistemas conectados.
  • Falta de controle sobre o que é recebido: como não existia um "formulário padrão", em teoria seria possível enviar informações que não deveriam poder ser alteradas por quem está usando o sistema.
  • Regras de conferência de dados espalhadas: as verificações de "esse dado está preenchido corretamente?" ficavam misturadas com a própria estrutura de arquivamento do banco de dados, dificultando manter tudo consistente.
  • Atualizações pouco claras: quando um cadastro era editado, o sistema usava um mecanismo automático "por baixo dos panos" para decidir o que mudar, dificultando saber com exatidão o que uma edição realmente alterava.

5. Vantagens para as próximas etapas do projeto

Mais segurança

Só é possível enviar exatamente os dados previstos no formulário de cada cadastro — nada além disso.

Mais estabilidade

Ajustes internos no banco de dados não afetam automaticamente o que é mostrado na tela, evitando quebras inesperadas.

Conferência de dados mais clara

Todas as regras de "o que é um cadastro válido" agora estão concentradas num único lugar, mais fácil de revisar e ajustar.

Edições mais transparentes

Ficou explícito, campo por campo, o que acontece quando um cadastro é atualizado — sem mecanismos automáticos ocultos.

Flexibilidade futura

Será possível, por exemplo, mostrar uma versão resumida de um cadastro em uma tela e uma versão completa em outra, sem mexer na forma como os dados são guardados.

Padrão pronto para repetir

O modelo criado (formulário de entrada + comprovante de saída) já foi testado nos quatro tipos de cadastro do sistema, incluindo o caso mais complexo — novos cadastros futuros podem seguir a mesma receita.

Em resumo: essa etapa não adicionou uma funcionalidade nova visível para quem usa o sistema — foi um ajuste de organização interna que deixa o sistema mais seguro, mais fácil de manter e mais preparado para receber novas funcionalidades nas próximas etapas do projeto.
