Análise arquitetural do backend

Um raio-x do estado atual do sistema que recebe e organiza os cadastros (o "backend"), destacando o que já está sólido, o que precisa ser ajustado para manter tudo coerente, o que ainda falta construir, e em que ordem seguir daqui para frente.

1. Por que essa análise foi feita

Este é um projeto de iniciação científica, e por isso a forma como o sistema é construído importa tanto quanto o sistema funcionar. Não basta que os cadastros "funcionem hoje" — é preciso que as decisões de organização interna sejam consistentes entre si e continuem fazendo sentido conforme o sistema cresce, para que o trabalho possa ser explicado, avaliado e retomado com segurança a qualquer momento.

Esta análise revisou todo o código do backend do Sistema ONG Animal — a parte do sistema responsável por receber os pedidos da tela (cadastrar um animal, um adotante, etc.), aplicar as regras do negócio e guardar tudo de forma organizada no banco de dados. O resultado está dividido em quatro partes: o que já está bem estabelecido, o que precisa ser alterado por já existir mas estar inconsistente, o que precisa ser adicionado por ainda não existir, e um roteiro de próximos passos.

2. O que já está bem estabelecido

Antes de falar do que falta, vale registrar a base que já está consolidada — é sobre ela que os próximos passos devem ser construídos, não ao lado dela.

Organização em camadas

O sistema segue um fluxo único e previsível: a "porta de entrada" recebe o pedido, uma camada de regras de negócio decide o que fazer, e só então o dado chega ao banco. Esse fluxo é usado por igual nos quatro tipos de cadastro (adotante, animal, raça, espécie).

Formulário/comprovante separado do arquivamento

Como já registrado no relatório de migração anterior, a tela troca informações com a API usando um "formulário de entrada" e um "comprovante de saída" próprios, sem expor diretamente a estrutura interna de arquivamento do banco.

Tratamento de erros centralizado

Existe um único ponto do sistema responsável por transformar qualquer erro interno em uma resposta padronizada e compreensível — por exemplo, "cadastro não encontrado" ou "este dado já está em uso" —, evitando que cada tela precise interpretar erros de formatos diferentes.

Histórico do banco de dados versionado

Toda alteração na estrutura do banco de dados fica registrada em um histórico sequencial e datado, com dados de teste próprios — permite reconstruir o banco do zero, de forma confiável, em qualquer máquina.

3. O que precisa ser alterado

Estes são pontos que já existem no sistema, mas que se desviaram do padrão adotado no restante do backend — corrigi-los antes de adicionar funcionalidades novas evita que a inconsistência se espalhe.

Inconsistência no tratamento de erro

Dois cadastros respondem "não encontrado" de um jeito diferente dos outros

No cadastro de Animal e no de Raça, quando alguém tenta cadastrar ou atualizar um registro referenciando uma raça, espécie ou adotante que não existe, o sistema responde como se fosse um erro de "dado inválido" — em vez de responder como "referência não encontrada", que é o comportamento padrão em todo o resto do sistema. Ou seja, existem hoje dois caminhos diferentes para a mesma situação, dependendo de qual tela originou o pedido.

Por que corrigir: o restante do sistema já tem um tratamento único e automático para "referência não encontrada" — esses dois pontos remam contra a própria decisão arquitetural já tomada, e deixam a resposta da API imprevisível para quem for consumi-la (inclusive o próprio frontend).

Documentação interna desatualizada

A "planta baixa" do backend não reflete mais o código real

O documento interno que descreve a arquitetura do backend (usado como referência rápida ao trabalhar no código) ainda descreve um estágio anterior do projeto — antes da introdução do formulário/comprovante separado do arquivamento interno, e antes de as atualizações de cadastro passarem a ser feitas campo por campo de forma explícita. O texto atual descreve um mecanismo automático de atualização que não é mais o usado no cadastro de Animal.

Por que corrigir: esse documento é a referência rápida de como o sistema é organizado — se ele não acompanha o código, deixa de cumprir seu papel e pode levar a decisões futuras baseadas em uma descrição que não existe mais.

Assimetria não documentada

Um dos quatro cadastros não tem o mesmo ciclo completo dos outros

Adotante, Animal e Raça permitem cadastrar, editar, consultar e excluir. Espécie permite apenas consultar. Não há, hoje, nenhum registro explicando se essa limitação é uma decisão deliberada (por exemplo, porque a lista de espécies é fixa e não deve ser editada por quem usa o sistema) ou uma funcionalidade que ainda falta implementar.

Por que corrigir: uma assimetria entre cadastros que deveriam seguir o mesmo padrão, sem justificativa registrada, é o tipo de coisa que passa a impressão de inacabado numa avaliação — mesmo que tenha sido uma escolha consciente.

4. O que precisa ser adicionado

Estas são lacunas — coisas que ainda não existem no sistema e que, em algum momento do projeto, precisarão existir.

Maior risco

Praticamente não há testes automatizados

Hoje existe apenas uma verificação de que "o sistema liga sem erro". Não há nenhuma verificação automática de que as regras de negócio continuam funcionando — por exemplo, a regra de que um animal só pode ficar com status "adotado" se estiver de fato vinculado a um adotante.

Por que importa: sem testes, cada nova alteração corre o risco de quebrar uma regra já existente sem que ninguém perceba na hora — o problema só aparece depois, e sem um teste automatizado ninguém fica sabendo exatamente quando ou por quê.

Segurança

A API está totalmente aberta

Não existe, hoje, nenhum controle de quem pode consultar ou alterar os dados — qualquer pessoa com acesso ao endereço da API consegue cadastrar, editar ou excluir qualquer registro.

Por que importa: mesmo que esteja fora do escopo imediato do PIVIC, é uma lacuna relevante de se registrar formalmente, já que se torna indispensável assim que o sistema deixar de ser apenas um protótipo acadêmico.

Documentação técnica

Não existe um "manual" gerado automaticamente da API

Não há hoje nenhum documento (gerado a partir do próprio código, sempre atualizado) listando todos os pedidos que a API aceita e o formato esperado de cada um.

Por que importa: isso dificulta a integração com a tela (que é um projeto separado, em Angular) e torna mais difícil para qualquer avaliador entender rapidamente o que a API oferece sem precisar ler o código.

Regras de negócio pendentes

Validações já sinalizadas no próprio código, mas ainda não implementadas

O código já contém anotações próprias marcando pendências conhecidas: falta validar a idade informada de um adotante, falta impedir que a data de saída de um animal seja anterior à data em que ele foi resgatado, falta implementar a exclusão "reversível" de um animal (hoje a exclusão remove o registro em definitivo), e falta validar se um contato duplicado pode ser cadastrado mais de uma vez.

Por que importa: são pendências que o próprio código já reconhece — deixá-las paradas por muito tempo aumenta o risco de dados inconsistentes entrarem no banco.

Configuração de ambiente

Não existe um modelo de configuração para rodar o projeto do zero

As credenciais de acesso ao banco de dados não vêm preenchidas nem existe um arquivo de exemplo mostrando quais informações precisam ser configuradas antes de rodar o sistema pela primeira vez.

Por que importa: dificulta que outra pessoa (ou o próprio autor, em outro computador) consiga colocar o projeto para rodar sem precisar adivinhar a configuração necessária.

Verificação contínua

Não há verificação automática antes de aceitar uma mudança no código

Hoje, qualquer alteração pode ser incorporada ao projeto sem que nada rode automaticamente para conferir se algo quebrou.

Por que importa: só faz sentido investir nisso depois que existirem testes automatizados de fato — é o próximo passo natural depois da maior lacuna identificada nesta análise.

5. Próximos passos fundamentais

Os pontos acima foram organizados em uma ordem pensada especificamente para preservar a coerência da arquitetura: primeiro alinhar o que já existe, depois proteger o que existe com testes antes de continuar crescendo, e só então avançar para funcionalidades que ampliam o sistema.

  1. Curto prazo
    Alinhar o que já existe ao padrão do restante do sistema
    Corrigir os dois pontos de tratamento de erro divergentes (Animal e Raça); decidir e registrar formalmente se o cadastro de Espécie é mesmo só de consulta; atualizar a documentação interna do backend para refletir a arquitetura real. Nenhum desses passos adiciona funcionalidade nova — apenas remove inconsistências antes que se acumulem mais.
  2. Médio prazo
    Proteger as regras de negócio com testes antes de continuar
    Criar testes automatizados cobrindo as regras centrais de cada cadastro (a mais crítica sendo a relação entre status "adotado" e vínculo com um adotante); implementar as validações de negócio já sinalizadas como pendentes no código; criar um arquivo de exemplo de configuração de ambiente. Fazer isso antes de novas funcionalidades evita crescer o sistema sobre uma base que ninguém consegue verificar automaticamente.
  3. Longo prazo
    Ampliar o sistema com o que hoje está fora do escopo
    Autenticação e controle de acesso; documentação automática da API; verificação automática a cada mudança no código. São passos que dependem da base anterior estar sólida — tentar adicioná-los antes tende a gerar mais retrabalho do que ganho.

Glossário

API
"Porta de entrada" do sistema, que recebe pedidos da tela e devolve respostas.
Controller
Parte da API responsável por atender cada tipo de pedido (cadastrar, editar, consultar).
DTO
Formulário/comprovante usado só para troca de informação entre a tela e a API, separado de como o dado é guardado.
Entidade
Estrutura de dados que representa uma tabela do banco de dados.
Migração de banco
Registro histórico e sequencial de cada alteração feita na estrutura do banco de dados.
Testes automatizados
Verificações programadas que checam se as regras do sistema continuam funcionando a cada mudança no código.
Autenticação/autorização
Mecanismo que identifica quem está usando o sistema e controla o que essa pessoa pode ou não fazer.
Verificação contínua
Processo automático que roda os testes a cada alteração, antes de aceitar a mudança no projeto.

Em resumo: a arquitetura de base do backend está sólida e consistente — o maior risco atual não é a organização geral, e sim o acúmulo de pequenos desvios pontuais e a ausência de testes automatizados. Corrigir os desvios e proteger as regras de negócio com testes antes de seguir adicionando funcionalidades é o que garante que a coerência arquitetural, tão relevante para este trabalho de iniciação científica, se mantenha ao longo de todo o projeto.
